When I ran cpu, memory, and disk load together, `free -h` showed available memory drop fast and `dmesg | grep -i oom` actually caught the kernel killing a process to free up memory. The tmpfs fill-up was less dramatic — once it hit the 256M cap, `dd` just failed with "No space left on device" and stopped. If this were a real production server, I'd want monitoring to alert before things get anywhere near the OOM killer, not after, and I'd keep a second way to access the server before pushing any SSH config changes — I locked myself out of my own session testing `AllowUsers` and on a real remote box that could've meant losing access completely.
